\section{Codec and Measurement Architecture}
The codec partitions a stream into blocks of at most 2048 samples. Each block evaluates constant, harmonic, and linear predictors from decoder-visible state. Residual moments parameterize a generalized-error model, and the rate controller selects an entropy-constrained codebook whose serialized record remains within the requested budget. Sixteen interleaved rANS states amortize renormalization dependencies while preserving deterministic scalar decoding. CRC32-C protects each block body. Indexed streams append byte offsets and sample ranges under a footer checksum, allowing a validated binary search followed by decoding of only intersecting records.

The C++ implementation dispatches scalar, AVX2/FMA, AVX-512, or ARM Neon kernels after runtime capability checks. Distribution builds retain conservative \texttt{-O1 -g0} compilation, disabled link-time optimization, and one-job build pools; host-native optimization is opt-in. The C ABI owns no persistent codec object and accepts caller-owned input and output spans. Go passes slice storage directly through cgo, while the safe Rust layer confines raw pointers to a private FFI module.

\subsection{Counter methodology}
The profiling harness executes a warmed encode/decode loop under \texttt{perf stat}. It requests cycles, instructions, L1 data-cache loads and misses, branch instructions, and branch misses. From raw counts it computes instructions per cycle, L1 miss fraction, and branch-misprediction fraction. Counter availability is reported per event rather than inferred from a zero count. If kernel policy or virtualization prevents hardware access, the artifact records the diagnostic and falls back to monotonic wall-clock timing.

The Roofline point separates measurements from models. Sustained memory bandwidth is estimated by repeated copies over a working set larger than the detected last-level cache. Codec traffic counts one source read, one reconstructed write, and encoded writes and reads. Floating-point and integer operations per sample are an explicit command-line model parameter, not a hardware-counter claim. Arithmetic intensity is the modeled operation count divided by modeled traffic; the plotted attainable rate is the lesser of the supplied processor issue ceiling and the measured bandwidth ceiling.
